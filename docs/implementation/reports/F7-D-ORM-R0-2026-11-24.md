# F7-D-ORM-R0 — Contrato técnico de reconciliación ORM y esquema

**Fecha:** 2026-11-24  
**Rama de referencia:** `feature/f7-e4-implementation`  
**Estado:** B1 decidido; B2 preflight completado en `evoworld_test` (PostgreSQL) sin tablas de aplicación; otras BDs objetivo siguen pendientes de inspección; B3 resuelto por DEC-F7D-20 y reflejado en contrato y prueba. No autoriza implementación.  
**Alcance:** reconciliar los modelos SQLAlchemy, el esquema físico y las migraciones de F7-D Nivel 1 con los contratos aprobados. No reabre el diseño funcional de F7-D.

## 1. Dictamen

La inspección de la rama confirma una incompatibilidad estructural, no una mera expectativa obsoleta de pruebas:

1. `ChallengeOperationRow` representa actualmente un esquema de operación de mundo/F7-C (`operation_id`, `status`, `continuity_state`, `requesting_user_id`, `engine_version`, `checkpoint_id`, `recovery_generation`), mientras que el servicio y el repositorio F7-D consultan y escriben `actor_user_id`, `operation` y `outcome`. La tabla propia de procedencia de F7-D no está representada por el modelo ORM.
2. Los modelos `ChallengeRow` y `ChallengeParticipantRow` no expresan varias columnas, nulabilidades, claves foráneas y restricciones exigidas por el contrato y por las pruebas de esquema.
3. `ensure_schema()` no contiene migraciones F7-D para reconciliar tablas existentes; `Base.metadata.create_all()` crea tablas ausentes, pero no corrige tablas existentes ni añade las columnas/restricciones faltantes.
4. Existe una discrepancia de diseño pendiente sobre la idempotencia de `create`: el esquema actual coloca `client_idempotency_key` y `request_hash` en `challenges`, mientras que §17.2 y §17.7 describen `challenge_operations` como registro propio de procedencia y §17.13 define un ámbito que incluye `challenge_id`, todavía inexistente antes de crear el desafío.

No se debe solucionar el punto 1 mediante alias entre `actor_user_id` y `requesting_user_id`: eso ocultaría la mezcla de dos semánticas distintas.

## 2. Fuentes contractuales que se preservan

- `CONTRACTS.md` §17.2: entidades `challenges`, `challenge_participants` y tabla propia `challenge_operations`.
- §17.7: procedencia auditable de las operaciones globales de desafío; no reutilizar `operation_resolutions` de F7-C.
- §17.13: atomicidad e idempotencia de operaciones globales, clave de cliente obligatoria en HTTP, hash canónico y conflicto 409 ante reutilización con contenido diferente.
- §17.14 y DEC-F7D-19: estados de resultados, `result_status` como fuente de verdad y sincronización de `result_verified`.
- DEC-F7D-14/15/16/17/18/19: preparación de mundos después del cierre de inscripción, operaciones globales atómicas, retención histórica, unicidad global de `world_id`, máquina de estados y procedencia.
- F7-C permanece intacta: `world_operations`, `world_events` y `operation_resolutions` conservan su semántica T1/T2 por mundo.
- F7-E.2-I permanece intacta: los mundos se eliminan lógicamente mediante `deleted_at`; este contrato no autoriza borrados físicos ni cascadas que destruyan su historia.

## 3. Esquema ORM objetivo

La siguiente especificación expresa el contrato que debe implementar el ORM. Los tipos concretos SQLAlchemy pueden adaptarse a SQLite y PostgreSQL sin alterar nulabilidad ni semántica.

### 3.1 `challenges`

| Campo | Regla |
|---|---|
| `id` | PK autoincremental, no nulo |
| `organizer_user_id` | FK a `users.id`, no nulo; conservar la política de borrado de organizador ya exigida por el test contractual |
| `name` | no nulo |
| `config_json` | no nulo; configuración congelada/versionada |
| `rules_version` | no nulo |
| `duration_ticks` | no nulo |
| `state` | no nulo; CHECK `ck_challenge_state` con el conjunto de estados de §17.3 |
| `created_at` | no nulo, UTC |
| `closed_at` | nullable |
| `completed_at` | nullable |

No se incorporan campos de procedencia duplicados a esta tabla salvo que una DEC resuelva expresamente el caso de idempotencia de creación descrito en §6.

### 3.2 `challenge_participants`

| Campo | Regla |
|---|---|
| `id` | PK autoincremental, no nulo |
| `challenge_id` | FK a `challenges.id`, no nulo, ON DELETE CASCADE |
| `user_id` | FK a `users.id`, no nulo, ON DELETE CASCADE |
| `world_id` | FK a `worlds.id`, nullable durante la inscripción/preparación; sin ON DELETE CASCADE |
| `state` | no nulo; estados de participación definidos por F7-D |
| `joined_at` | no nulo, UTC |
| `public_alias` | no nulo; alias público/seudónimo, nunca sustituye a la identidad interna |
| `result_json` | nullable |
| `result_status` | no nulo, con valor inicial contractual `persisted` solo cuando exista resultado persistido; sus valores/transiciones se rigen por §17.14 |
| `result_verified` | no nulo, booleano 0/1; derivado/sincronizado desde `result_status`, no fuente de verdad independiente |

Restricciones:
- UNIQUE `(challenge_id, user_id)`.
- UNIQUE global sobre `world_id` (los NULL previos a preparación pueden repetirse conforme a la semántica SQL de ambos motores).
- CHECKs de estados/booleanos conforme al contrato aprobado.
- FK `world_id → worlds.id` sin cascada destructiva. La eliminación lógica del mundo no elimina la participación ni su resultado histórico.
- Mantener la semántica sentinel `world_id = 0` solo donde el flujo B3-5-FIX2 la requiera expresamente; el campo nullable representa ausencia relacional real. No convertir automáticamente 0 en NULL ni viceversa sin contrastar los callers y las pruebas.

### 3.3 `challenge_operations`

Debe ser una tabla F7-D independiente, no una variante de `world_operations`:

| Campo | Regla |
|---|---|
| `id` | PK autoincremental, no nulo |
| `challenge_id` | FK a `challenges.id`, no nulo |
| `operation` | VARCHAR(32), no nulo; vocabulario de §17.2 |
| `actor_user_id` | FK a `users.id`, no nulo; actor autenticado validado en servidor |
| `client_idempotency_key` | VARCHAR(64), no nulo |
| `request_hash` | VARCHAR(64), no nulo; SHA-256 canónico conforme a §17.13 |
| `outcome` | VARCHAR(32), nullable según operación |
| `created_at` | timestamp UTC, no nulo |

La restricción de idempotencia para operaciones sobre un desafío debe corresponder exactamente al ámbito aprobado en §17.13: `(challenge_id, actor_user_id, client_idempotency_key)`. El registro se inserta con `flush()` en la misma transacción que los cambios de estado/relaciones y se confirma en el mismo COMMIT.

No añadir `operation_sequence`, `continuity_state`, `checkpoint_id`, `recovery_generation` ni estados T1/T2 a esta tabla. No reutilizar `operation_resolutions`.

**Nota:** §17.2 especifica `request_hash` no nulo con default vacío en su tabla, mientras §17.13 y la validación HTTP exigen hash canónico. La implementación debe almacenar el hash calculado por el servidor; el default vacío no debe convertirse en una vía alternativa que eluda el contrato HTTP.

## 4. Migraciones requeridas

La implementación futura deberá incorporar migraciones explícitas e idempotentes dentro del mecanismo aprobado `ensure_schema()` (DEC02), para SQLite y PostgreSQL.

1. Inspeccionar tablas, columnas, índices, constraints, FKs y recuentos antes de ejecutar DDL.
2. Crear las tablas F7-D ausentes con el esquema contractual.
3. Para tablas existentes, añadir/reconstruir únicamente lo necesario y de forma transaccional, preservando filas y relaciones.
4. Crear o validar `closed_at`, `completed_at`, `joined_at`, `public_alias`, `result_status`, nulabilidad de `world_id` y `result_json`, `result_verified`, FKs, UNIQUE y CHECKs.
5. Migrar `challenge_operations` desde el esquema incompatible solo si se demuestra que cada fila puede mapearse sin pérdida ni cambio de significado. No mapear `requesting_user_id` a `actor_user_id` por simple equivalencia nominal, ni interpretar campos F7-C como operaciones F7-D.
6. Si la tabla incompatible contiene filas que no puedan clasificarse/migrarse de forma inequívoca, abortar con diagnóstico explícito y rollback completo. Prohibido truncar, borrar o recrear la tabla para hacer pasar las pruebas.
7. Validar integridad referencial tras la migración; en SQLite, ejecutar `PRAGMA foreign_key_check`.
8. La migración repetida debe ser idempotente y no rebajar restricciones ni reescribir datos sanos.
9. No modificar `worlds` para añadir `challenge_id`; no tocar tablas F7-C ni su secuencia durable.

Los detalles de reconstrucción de tablas SQLite y de validación de constraints PostgreSQL se especificarán en el plan de implementación, después de resolver los bloqueos de §6. No se ejecuta ninguna migración en esta fase documental.

## 5. Compatibilidad y preservación

- Preservar la API, los servicios, la máquina de estados y las decisiones F7-D Nivel 1 aprobadas; esta reconciliación es de persistencia/ORM, no una ampliación funcional.
- Preservar idempotencia HTTP: `Idempotency-Key` obligatorio, validado; mismo hash devuelve resultado original; hash distinto produce 409; comprobación antes de retornos tempranos por estado.
- Preservar atomicidad: registro de procedencia y cambio de estado dentro de una única transacción.
- Preservar los resultados confirmados, disputados e invalidados y sus transiciones; `result_status` continúa siendo fuente de verdad.
- Preservar F7-C y F7-E sin cambios de semántica.
- No usar `Base.metadata.create_all()` como sustituto de migraciones sobre tablas existentes.

## 6. Bloqueos que requieren decisión explícita antes de implementar

### B1 — Idempotencia de `create_challenge` — decisión adoptada

**Decisión:** separar la idempotencia de creación del registro de procedencia `challenge_operations`, mediante una tabla propia `challenge_creation_requests`. Esta tabla resuelve la ausencia inicial de `challenge_id` sin introducir un ID ficticio ni alterar el ámbito de idempotencia de las operaciones sobre desafíos existentes.

Esquema contractual mínimo:

| Campo | Regla |
|---|---|
| `id` | PK autoincremental |
| `actor_user_id` | FK a `users.id`, no nulo |
| `client_idempotency_key` | VARCHAR(64), no nulo |
| `request_hash` | VARCHAR(64), no nulo; hash canónico SHA-256 calculado por el servidor |
| `challenge_id` | FK a `challenges.id`, no nulo al confirmar la transacción; UNIQUE |
| `created_at` | timestamp UTC, no nulo |

Restricciones e invariantes:

1. UNIQUE `(actor_user_id, client_idempotency_key)`; el ámbito de creación es independiente del ámbito de operaciones `(challenge_id, actor_user_id, client_idempotency_key)` de §17.13.
2. La reserva de la clave, la inserción del desafío y la asociación de `challenge_id` se realizan en una única transacción. Ningún registro incompleto puede quedar confirmado: la fila de solicitud solo se hace durable junto con el desafío asociado.
3. Mismo actor, misma clave y mismo hash: recuperar y devolver el desafío originalmente asociado, sin crear otro.
4. Mismo actor y misma clave con hash diferente: responder `409 Conflict`; no crear ni modificar un desafío.
5. Ante solicitudes concurrentes con la misma clave, la restricción UNIQUE es la autoridad final. La ruta que pierde la carrera debe deshacer su transacción, volver a consultar la fila ganadora y aplicar la comparación de hash; no debe traducir cualquier error de integridad indiscriminadamente a éxito.
6. `challenge_operations` sigue registrando únicamente operaciones sobre un desafío ya existente. No duplicar allí el evento de creación ni reutilizar `operation_resolutions` de F7-C.
7. No mantener también `client_idempotency_key` y `request_hash` como segunda fuente de verdad en `challenges`. Su eventual retirada o migración desde columnas existentes debe hacerse preservando datos y resolverse en el plan de implementación; no se autoriza borrar datos en esta fase.

La implementación deberá verificar estas garantías en SQLite y PostgreSQL, incluidos reintentos secuenciales, concurrencia, hash distinto y rollback antes del COMMIT.

### B2 — Filas preexistentes en `challenge_operations` — dictamen de inspección

La inspección de la rama confirma que el modelo ORM actual de `challenge_operations` contiene columnas de protocolo de mundo/F7-C y no el esquema propio F7-D. `ensure_schema()` ejecuta `Base.metadata.create_all()`, pero no contiene una migración F7-D de esta tabla ni una inspección de sus filas. La fuente versionada, por sí sola, no permite afirmar cuántas filas existen en cada base de datos real ni qué semántica tienen.

**Preflight ejecutado — PostgreSQL `evoworld_test` (2026-11-24):**

- Conexión confirmada: `current_database() = evoworld_test`, `current_user = evoworld_test`.
- Esquemas existentes: únicamente `information_schema`, `pg_catalog`, `pg_toast` y `public`.
- `public` no contiene ninguna tabla de aplicación (`information_schema.tables`, `table_type = BASE TABLE`): cero tablas en total.
- No existe `challenge_operations`, ni tablas con nombres relacionados con `challenge`, `operation` o `participant`.
- No existe `alembic_version`.
- Por tanto, en esta base no hay filas preexistentes que clasificar ni restricciones/índices/FKs de `challenge_operations` que inspeccionar. El error de consulta contra `public.challenge_operations` se debió a que la relación no existe; no es evidencia de pérdida o corrupción.
- No se ejecutó DDL ni ninguna escritura.

**Dictamen acotado:** el preflight de `evoworld_test` queda completado y confirma una base PostgreSQL sin tablas de aplicación. No hay datos F7-C/F7-D preexistentes en esta instancia que requieran reconciliación. Este resultado no se extrapola a ninguna otra BD, entorno o archivo.

**Resultado general:** B2 queda resuelto como protocolo de seguridad; el preflight está completado únicamente para `evoworld_test`. La clasificación de datos sigue pendiente para cada otra BD objetivo antes de implementar. Cada preflight deberá:
1. Identificar el motor, ruta/identificador y esquema exacto sin escribir.
2. Obtener columnas, constraints, índices, FKs y `COUNT(*)` de `challenge_operations`.
3. Si hay filas, inspeccionar solo los campos necesarios para clasificarlas, sin exponer payloads sensibles.
4. Clasificar cada fila como F7-C/operación de mundo, F7-D/procedencia de desafío, ambigua o huérfana, apoyándose en evidencia de relaciones y semántica; no solo en nombres parecidos.
5. Detener la migración si hay filas ambiguas, huérfanas o no mapeables; no renombrar, truncar, borrar ni convertir automáticamente `requesting_user_id` en `actor_user_id`.
6. Emitir un informe de conteos y plan de preservación antes de cualquier DDL.

La inspección de esquema descrita arriba se realizó exclusivamente sobre la instancia PostgreSQL de pruebas `evoworld_test` del contenedor autorizado `evoworld-f7e-pg-test`, en modo de solo lectura. No se abrió ni modificó ninguna BD local protegida o de producción. Para cualquier otra instancia, no se presume que la tabla esté vacía.

### B3 — Discrepancias contractuales de constraints — dictamen

**Resuelto:** DEC-F7D-01 contiene una referencia histórica a `ON DELETE CASCADE` en `challenge_participants.world_id`, pero DEC-F7D-16 y CONTRACTS §17.2 corrigen explícitamente esa política para preservar historia. Prevalece la decisión posterior DEC-F7D-16 y el contrato §17.2: sin cascada destructiva en la FK de `world_id`. También prevalece UNIQUE global sobre `world_id` (DEC-F7D-17), no UNIQUE compuesto con `challenge_id`.

**Resuelto por DEC-F7D-20 (2026-11-24):** `challenges.organizer_user_id` usa `ON DELETE RESTRICT` (o equivalente `NO ACTION`). El borrado físico de una cuenta organizadora se rechaza mientras existan desafíos vinculados; anonimización o desvinculación requerirá un procedimiento separado y auditable. La decisión quedó incorporada en `DECISIONS.md`, `CONTRACTS.md` §17.2 y `tests/test_f7d_challenges.py`, que ahora exige `RESTRICT`.

Los CHECK exactos deben derivarse de los vocabularios vigentes de §17 y de las transiciones aprobadas; no introducir cambios semánticos silenciosos durante la reparación ORM.

## 7. Matriz mínima de aceptación futura

La implementación no se considerará aceptada hasta verificar, como mínimo:

- [ ] Inspección de esquema limpio y legado en SQLite.
- [ ] Inspección/migración en PostgreSQL real.
- [ ] Columnas, nulabilidades, PK, UNIQUE, CHECK e índices de las tres tablas.
- [ ] FKs y políticas ON DELETE exactas, incluyendo retención histórica.
- [ ] `ChallengeOperationRow` expone todos y solo los campos F7-D definidos.
- [ ] Operaciones de creación, transición, inscripción, preparación, inicio, disputa, resolución y completitud dejan procedencia correcta.
- [ ] Reintento igual devuelve resultado original; misma clave con hash diferente devuelve 409.
- [ ] Fallo antes del COMMIT no deja ni estado parcial ni registro de procedencia huérfano.
- [ ] Migración repetida no altera datos ni restricciones ya correctos.
- [ ] Migración con datos incompatibles aborta sin pérdida.
- [ ] B35 FIX2 se valida sin monkeypatch, alias ORM ni captura que oculte el defecto de modelo.
- [ ] Regresión focalizada F7-D/B35 y regresión global documentadas por separado; no atribuir fallos a F7-E sin evidencia causal.

## 8. Fuera de alcance y autorización

Este documento no autoriza:
- cambios en código, ORM, migraciones, pruebas, contratos aceptados o base de datos;
- eliminación/recreación de tablas o filas históricas;
- monkeypatches, alias de compatibilidad que oculten el modelo incorrecto, ni exclusiones masivas de pruebas;
- cambios a F7-C, F7-E o F7-D Nivel 2;
- commit adicional, PR o merge distintos de la incorporación de este documento.

**Siguiente gate:** ejecutar el preflight B2 sobre cada BD objetivo y documentar su clasificación antes de diseñar/ejecutar la migración. La implementación requerirá autorización expresa independiente.
